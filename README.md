# ClassGame

**ClassGame** is a 3D educational game where an autonomous AI tutor leads each student through a learning mission, asks clarifying questions, takes structured notes, and adapts the path based on the student's progress and feedback.

The project is designed for the **All Things Agentic Hackathon** as a **Collaborative Partner** agent. The Three.js game is the interactive learning interface, while the real product is the agent behind it: a tutor that leads the way, keeps notes about how the student thinks, captures feedback, remembers mistakes, adjusts difficulty, generates new exercises, and decides what the student should practice next.

The experience must be **responsive and mobile-first**. The first usable version should work well on a phone screen, then scale up to tablets and desktop. The 3D scene, quiz panels, tutor dialogue, and progress UI should avoid fixed desktop-only layouts.

Hackathon page: [All Things Agentic Hackathon](https://allthingsagentichackathon.devpost.com/)

## Core Idea

Students enter a small 3D learning observatory. Each room represents part of a study journey:

- **Central Hall**: shows the student's progress and available topics.
- **Diagnostic Room**: asks initial questions to estimate the student's current level.
- **Practice Room**: presents interactive challenges generated by the agent.
- **Reinforcement Room**: opens automatically when the agent detects a weak skill.
- **Mastery Room**: gives a final personalized challenge before the student advances.

The Gemini-powered tutor appears as a holographic guide. It is not just a chatbot. It makes learning decisions autonomously and changes the game flow based on evidence from the student's answers.

## Collaborative Partner Alignment

ClassGame should directly satisfy the Collaborative Partner challenge:

> Build an agent that leads the way and takes notes. It should ask clarifying questions, guide the user step-by-step, and have a clear way to capture feedback, so it constantly adapts to the user's unique way of thinking.

The MVP should make this visible in the product, not just describe it in the README:

- **Leads the way**: the tutor chooses the next learning step and tells the student what to do next.
- **Asks clarifying questions**: before giving another exercise, the tutor asks what confused the student or why they chose an answer.
- **Guides step-by-step**: the tutor breaks a problem into smaller prompts instead of only marking answers right or wrong.
- **Takes notes**: the agent records observations such as "confuses numerator with denominator" or "prefers visual examples."
- **Captures feedback**: the UI should let the student mark an explanation as helpful, confusing, too easy, or too hard.
- **Adapts to thinking style**: future questions and explanations should use the captured notes and feedback.

## Example Flow

1. The student starts an Algebra mission.
2. The agent asks a short diagnostic quiz.
3. The student repeatedly misses questions involving fractions.
4. The agent identifies fractions as the underlying gap.
5. The game temporarily redirects the student to a reinforcement room.
6. Gemini generates new fraction exercises and explanations.
7. Progress is saved in Firestore.
8. Once the student improves, the next Algebra room unlocks.

## Why This Fits The Hackathon

This is an agentic education system, not a regular game or quiz app.

The agent:

- Maintains memory of the student's learning history.
- Uses multi-turn interaction to understand confusion.
- Generates personalized exercises.
- Evaluates answers and explains mistakes.
- Decides when to increase, reduce, or redirect difficulty.
- Updates the student's learning path without manual teacher input.

Primary category:

**The Collaborative Partner**

## Proposed Stack

- **Three.js**: 3D learning environment.
- **React / Next.js**: mobile-first web game frontend.
- **Go**: standalone agent API, following the same modular backend style used in `/Users/velrino/Documents/Projects/unshatter/api`.
- **Gemini 3.5+**: tutor reasoning, exercise generation, answer evaluation, explanations.
- **Google Genkit Go or ADK Go**: agent workflow framework.
- **Cloud Run**: deployed frontend service and deployed Go API service.
- **Firebase / Firestore**: the only database layer for student memory, progress, attempts, and agent decisions.
- **Redis**: job queue and ephemeral state for orchestrated agent work. It is not the source of truth.
- **Cloud Storage**: future optional storage for teacher-uploaded materials.

## Architecture Decision

For the hackathon MVP, ClassGame should be built as **one repository with two deployable services**:

- **Frontend**: Next.js / React / Three.js mobile-first web game.
- **API**: Go backend for the agent workflow, Gemini calls, Firestore memory, and game decisions.

This is a better fit now that the project can use more Google Cloud budget. It also creates a stronger production architecture for the hackathon demo while keeping the database layer simple.

Recommended project structure:

```txt
allthingsagentichackathon/
  apps/
    web/
      src/
        app/
          page.tsx             # Three.js learning game
        components/
        modules/
          game/
          tutor/
    api/
      cmd/
        api/
          main.go              # Go API entrypoint
      internal/
        app/
          server.go            # HTTP server setup
          error_handler.go
        config/
          config.go
          env_reader.go
          validation.go
        modules/
          agent/               # Gemini with Genkit Go or ADK Go tutor endpoints
          orchestrator/        # direct-vs-queued learning decision routing
          queue/               # Redis-backed agent jobs
          progress/            # student progress endpoints
          health/              # health/readiness endpoints
        shared/
          firebase/            # Firebase app and Firestore connection
          redis/               # Redis connection for jobs and ephemeral state
      infra/
        cloud-run/
          Dockerfile
      docs/
        architecture/
        endpoints/
        development/
```

The Go API should use the same general style as the existing Unshatter API:

- `cmd/api/main.go` as the entrypoint.
- `internal/app` for server setup and shared HTTP behavior.
- `internal/config` for environment parsing and validation.
- `internal/modules/*` for feature boundaries.
- `internal/shared/firebase` for Firebase and Firestore access.
- `internal/shared/redis` for Redis queue and ephemeral state access.
- `docs/` for endpoint and deployment notes.
- `infra/cloud-run/` for container/deployment files.

The main difference is that ClassGame should use **Firebase/Firestore as the only persistent database**. It should not include MongoDB, Cloud SQL, or another durable database in the MVP. Redis is used for queueing and short-lived orchestration state only.

Recommended runtime flow:

```txt
Three.js game on Next.js
  -> Go API /agent/answer
    -> Orchestrator
      -> direct response for simple validation
      -> Redis queued job for Gemini/adaptive tutor work
        -> Agent worker uses Genkit Go or ADK Go
        -> Gemini evaluates the answer
        -> Firestore saves memory and decision
        -> Redis stores short-lived job status
    -> Go API returns direct result or job id
  -> frontend updates room, dialogue, challenge, and progress UI
```

Cloud Run services:

```txt
classgame-web   # Next.js frontend
classgame-api   # Go agent API
```

If the Redis worker is split from the API process, reuse the same Go codebase and deploy a third Cloud Run service:

```txt
classgame-worker   # Go agent queue worker
```

For the fastest MVP, the Go binary can support both modes:

```txt
CLASSGAME_RUNTIME_MODE=api
CLASSGAME_RUNTIME_MODE=worker
```

This keeps the architecture serious enough for the hackathon without adding unnecessary infrastructure:

- The frontend and API can scale independently.
- Gemini credentials stay only in the Go API.
- Firestore remains the single source of truth for learning memory.
- The Go API can expose clean typed endpoints for the game.
- The architecture is easy to explain in the demo video and diagram.

Suggested API endpoints:

```txt
GET  /healthz
GET  /readyz
POST /agent/answer
GET  /agent/jobs/{jobId}
GET  /progress/{studentId}

```

Suggested Firestore collections:

```txt
students/{studentId}
students/{studentId}/attempts/{attemptId}
students/{studentId}/skills/{skillId}
students/{studentId}/decisions/{decisionId}
```

## Redis Queue And Orchestrator Decision

ClassGame should use a Redis-backed queue for agent work, inspired by the existing WhatsApp orchestrator pattern in `/Users/velrino/Documents/Projects/wpp/api`.

The orchestrator should decide whether a student event can be answered directly or needs an asynchronous agent job:

```txt
Student answer
  -> Go API /agent/answer
    -> Orchestrator
      -> direct_result, when no Gemini call is needed
      -> queued_result, when Gemini/adaptive reasoning is needed
```

Queued work should follow this shape:

```txt
Redis queue
  -> Agent worker
    -> load student context from Firestore
    -> call Gemini through Genkit Go or ADK Go
    -> classify weak skill
    -> decide next room/action
    -> save attempt, skill progress, and decision to Firestore
    -> save short-lived job result/status in Redis
  -> frontend polls GET /agent/jobs/{jobId}
```

Firestore remains the durable memory for attempts, skills, progress, and agent decisions. Redis should only hold queue jobs, temporary statuses, rate-limit counters, and cache entries that can be rebuilt.

- One tutor NPC/hologram.

- Visible agent notes panel for the demo.
- Student feedback capture for explanations and difficulty.
- Adaptive practice questions.
- Firestore-backed progress memory.
- Redis-backed queue for Gemini/adaptive tutor jobs.
- Visible "Agent Decision Log" panel for the demo.
- Cloud Run deployment for the Next.js frontend.
- Cloud Run deployment for the Go agent API.

## Mobile-First UX Requirements

ClassGame should be designed for mobile first, because many students will use learning tools from phones rather than desktops.

Core requirements:

- The game must be playable on a modern mobile browser.
- The 3D camera and controls must work with touch input.
- Quiz panels and tutor dialogue must fit small screens without overlapping the 3D scene.
- Buttons and answer options must be large enough for touch.
- The progress and agent decision log should be collapsible on mobile.
- Desktop should enhance the layout, not define the base experience.
- Text should remain readable without requiring pinch zoom.
- The demo should include at least one mobile viewport check.

## Agent Decisions To Demonstrate

The demo should clearly show the agent doing autonomous work:

- Detecting a weak skill from incorrect answers.
- Asking a clarifying question before deciding the next step.
- Taking a visible note about how the student is thinking.
- Capturing whether the explanation was helpful, confusing, too easy, or too hard.
- Changing the student's route inside the 3D world.
- Generating a new exercise set.
- Explaining why the student was redirected.
- Saving the decision and progress to Firestore.
- Unlocking the next room after improvement.
